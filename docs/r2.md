# File storage: Cloudflare R2

All uploads (panel and inverter pictures, utility bills, signed SP forms, the
As Built PV Layout, handover docs) go to a **private** R2 bucket. The code is
already in place (`api/_lib/storage.py`, `api/_routes/project_work.py`); it
needs a bucket and four environment variables. Without them, uploads go to
`web/.uploads/` on your laptop and are switched off on Vercel.

How it works:

1. The phone asks `POST /api/py/projects/<id>/upload-link` for permission. The
   server checks the person can upload that kind of file to that project now,
   then returns a 5-minute signed upload link. The link is locked to the
   file's exact type and size.
2. The phone uploads the file **straight to R2**. It never passes through
   Vercel, whose Hobby functions accept only about 4.5 MB per request.
3. The phone calls `POST /api/py/projects/<id>/files`. The server asks R2 what
   actually arrived, then records it in `project_files` (which is audited).
4. Viewing goes through `GET /api/py/files/<id>`, which checks access again
   and redirects to a 5-minute signed link. Nothing in the bucket is public.

Cost: 10 GB storage free, then US$0.015/GB-month. **Downloads are free** (no
egress fees), which is why R2 beats S3 for a photo-heavy app.

## Setup (about 15 minutes)

### 1. Turn on R2

1. Sign in at <https://dash.cloudflare.com> (create a free account if needed).
2. Left sidebar → **R2 Object Storage** → **Purchase R2 Plan / Enable R2**.
   Cloudflare asks for a card even for the free tier; you are not charged
   within the free allowance.

### 2. Create two buckets

Mirror the Neon branches, so test uploads never mix with customer files.

| Bucket name         | Used by                           |
| ------------------- | --------------------------------- |
| `gethomeapps-dev`   | your laptop, Vercel Preview + Dev |
| `gethomeapps-prod`  | Vercel Production only            |

For each: **Create bucket** → name it → **Location: Automatic** with
**location hint: Asia-Pacific (APAC)** → Default storage class → Create.
Leave **Public access disabled** (the default).

### 3. Allow the browser to upload (CORS)

Each bucket → **Settings** → **CORS Policy** → **Add CORS policy** → paste
(for `gethomeapps-prod`, delete the localhost line):

```json
[
  {
    "AllowedOrigins": [
      "https://homesapp-alpha.vercel.app",
      "http://localhost:3000"
    ],
    "AllowedMethods": ["PUT", "GET", "HEAD"],
    "AllowedHeaders": ["content-type"],
    "MaxAgeSeconds": 3600
  }
]
```

When you add a custom domain later, add it to `AllowedOrigins` too. Preview
deployments use one-off URLs; to test uploads on one, add its URL as well.

### 4. Create API tokens

R2 overview page → **Manage API tokens** (right side) → **Create API token**:

- Token name: `gethomeapps-dev`
- Permissions: **Object Read & Write**
- Specify bucket(s): **Apply to specific buckets only** → `gethomeapps-dev`
- TTL: Forever
- **Create**. Copy the **Access Key ID** and **Secret Access Key** now — the
  secret is shown once.

Repeat for `gethomeapps-prod`, scoped to that bucket only. Two tokens means a
leaked dev key cannot touch customer files.

Your **Account ID** is on the R2 overview page (right side).

### 5. Put the values in place

`web/.env.local` (development bucket):

```
R2_ACCOUNT_ID=<account id>
R2_ACCESS_KEY_ID=<dev access key id>
R2_SECRET_ACCESS_KEY=<dev secret>
R2_BUCKET=gethomeapps-dev
```

Vercel → project `homesapp` → Settings → Environment Variables:

| Name                   | Production         | Preview + Development |
| ---------------------- | ------------------ | --------------------- |
| `R2_ACCOUNT_ID`        | account id         | account id            |
| `R2_ACCESS_KEY_ID`     | prod key id        | dev key id            |
| `R2_SECRET_ACCESS_KEY` | prod secret        | dev secret            |
| `R2_BUCKET`            | `gethomeapps-prod` | `gethomeapps-dev`     |

Then **redeploy** — Vercel only applies new variables to new deployments.

### 6. Check it works

- **Live site:** <https://homesapp-alpha.vercel.app/api/py/ping> shows
  `"storage": "r2"` once the four settings are in. Then, signed in as a PM,
  go to **Account → File storage → Check file storage**. It makes one read
  request to R2 and should say *Working. Production uses the
  gethomeapps-prod bucket.* Otherwise it says what's wrong: a refused key, a
  missing bucket, or the dev bucket on production. (Run it from the app, not
  by opening `/api/py/storage/check` in its own tab: that sends a stale
  sign-in and gets "Your sign-in has expired".)
- **Laptop:** `npm run test:r2` runs the 39 tests that use the real dev
  bucket: about 85 requests with tiny files, all deleted, leaving the bucket
  empty. They cover the settings, the dev bucket, both buckets' CORS, and one
  project taken from creation to Ready for handover with every file in R2.
  `npm run test:py` skips them and never touches R2: in tests, uploads go to
  `web/.uploads/`.

### How files are laid out in the bucket

Filed by project, then type, then slot, so a project's photos and its
documents sit apart:

```
projects/{project id}/images/{slot}/{random id}.jpg      photos (JPEG, PNG, WebP, HEIC)
projects/{project id}/documents/{slot}/{random id}.pdf   documents (PDF)
profiles/{person id}/images/{random id}.jpg              profile pictures (512px squares)
```

The database records the same thing: `project_files.kind` is `image` or
`document`, and a PM's **Everyone's** files screen filters and counts by it.
`scripts/reorganize_files.py` moves files saved under the older layout
(`projects/{id}/{slot}/…`) into this one and updates their rows; it is safe
to run twice. On the dev bucket: `node scripts/py.mjs scripts/reorganize_files.py
--target dev`. On production it needs the `PROD_R2_*` keys and `--target
prod --confirm`.

### Abandoned uploads are cleared away

An upload is two steps: the app hands out a five-minute link, then the
browser tells it the file arrived. If the second step never comes (signal
lost, tab closed), a file sits in R2 that no project knows about. Every link
handed out is written down (`upload_intents`) and crossed off when its file is
registered. The 15-minute job (`.github/workflows/visit-reminders.yml`) deletes
whatever is left under links over a day old: one delete request each, and only
for those keys. Registered files, profile pictures, signed certificates and
files taken off a project (restorable from the audit log) are never touched.
Don't add an R2 lifecycle rule on `projects/` for this: it can't tell the
difference.
